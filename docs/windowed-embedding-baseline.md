# 긴 입력의 창 분할·평균 임베딩 비교

## 고정 조건과 방법

기존 다국어 MiniLM의 동일 revision·FP32 ONNX·CPU·masked mean·L2·cosine을 사용한다. 구조 청크 52개, 상대 경로·심볼 문맥화, 질문 v1의 answerable 24건, 근거 v1을 유지한다. 새 모델을 다운로드하거나 외부 추론을 사용하지 않았으며 API는 변경하지 않았다.

평가 전에 128토큰 창·32토큰 중첩을 Task log에 고정했다. 기존 문맥화 입력 전체를 tokenizer의 payload 토큰 순서대로 분할하고 각 창에 특수 토큰을 붙인다. 현재 모델에서는 특수 토큰 2개를 제외한 payload 최대 길이가 126이다. 메타데이터 접두는 첫 창에만 있으며 후속 창에 반복하지 않는다. 텍스트 디코딩·재인코딩으로 토큰을 바꾸지 않는다.

각 창의 masked mean·L2 벡터를 동일 가중 평균하고 다시 L2 정규화한다. 짧은 입력은 단일 창 벡터를 그대로 사용한다. 마지막 짧은 창도 동일 가중치이며 중첩 부분은 여러 창에 포함된다. 이는 전체 토큰을 한 번에 처리하는 모델이나 전체 토큰의 단순 평균과 같지 않다.

저장하는 벡터는 여전히 청크당 하나다. 원문·chunk ID·메타데이터·청크 개수는 변경하지 않는다. Chroma는 기존 기준선과 분리된 `data/chroma/windowed-multilingual-v1/`를 사용한다. 창 선택과 집계에 정답 출처·기대 심볼·근거 주석은 사용하지 않는다.

## 전체 입력 보존 검증

청크 52개에 대한 문맥화 입력은 총 61개 창으로 처리됐다. 44개는 한 창, 7개는 두 창, 1개는 세 창이다. 질문 24개는 모두 한 창이다. 기존에 앞부분만 사용하던 긴 청크 8개도 후미를 처리한다.

창별 payload를 중첩 32토큰만 제거해 이어 붙인 토큰열이 비절단 원래 토큰열과 정확히 같은지 검사했다. 문서 52개·질문 24개 모두 일치한다. 창 개수·원래/포함 payload 수·완전성·원문 character offset 범위를 결과 JSON에 기록했다.

초기 구현의 자동 tokenizer truncation·overflow 조합은 로컬 설치 환경의 테스트에서 후미를 누락했다. 비절단 payload 인코딩 → Encoding.truncate → 특수 토큰 post-process 순서로 수정하고 보존 테스트를 통과했다. 특정 라이브러리 전체의 결함이라고 일반화하지 않는다. 창 분할 tokenizer는 재사용해 반복 복사 비용을 줄였다.

## 결과

파일 순위는 전체 청크 검색 후 출처 중복을 제거해 평가한다.

| 임베딩 방식 | 파일 Hit@1 | 파일 Hit@3 | 파일 Hit@5 | 파일 MRR |
|---|---:|---:|---:|---:|
| 128토큰 앞부분 | 0.4583 | 0.8750 | 1.0000 | 0.6611 |
| 창 벡터 평균 | 0.4583 | 0.8333 | 1.0000 | 0.6646 |

MRR은 약 +0.0035지만 Hit@3은 낮아졌다. 파일 순위가 개선된 질문은 q002·q005, 회귀는 q007·q009·q010·q012, 동일은 18건이다. 작은 합성 평가셋의 미세한 평균 차이를 일반적 성능 향상으로 해석하지 않는다.

| 임베딩 방식 | 근거 완전 포함 @1 | @3 | @5 | @10 | 평균 원문 문자 수 @5 / @10 |
|---|---:|---:|---:|---:|---:|
| 128토큰 앞부분 | 5/24 | 7/24 | 9/24 | 13/24 | 1,298.5 / 2,348.0 |
| 창 벡터 평균 | 3/24 | 7/24 | 9/24 | 15/24 | 1,423.1 / 2,460.3 |

근거 완전 포함의 정의는 [기존 근거 평가](chunk-evidence-evaluation.md)를 유지한다. k는 실제 원문 청크 개수이며 출처를 중복 제거하지 않는다. 동일 k는 동일 토큰 또는 문자 사용량을 뜻하지 않는다.

추가로 양쪽 상위 10개에 동일 최대 10개·4,000자 제한을 적용했다. 원문 청크가 넘치면 통째로 건너뛰는 기존 예산 규칙이다. 근거 완전 포함은 각각 13/24·15/24로 유지됐고 평균 문맥은 2,336.0·2,425.2자, 최대는 3,767·3,653자였다. 이 역시 같은 상한 비교이며 동일한 실제 사용량 비교는 아니다.

## 개선과 회귀

- @5 개선: q005·q017. 회귀: q002·q007. 총 성공 수는 같다.
- @10 개선: q005·q012. 기존 @10 성공 13건은 유지한다.
- q012: 잘렸던 테이블 정의를 포함한 TRANSACTION-POST WORKING-STORAGE SECTION이 10위로 들어왔다.
- q011: 적재 문단의 후미 토큰도 처리하지만 LOAD-TRANSACTIONS는 여전히 상위 10개에 없었다.

전체 토큰을 처리하면 모든 질문이 해결된다는 가설은 지지되지 않았다. q012 개선도 전체 창 집계로 나타난 결과이며 후미의 특정 구절만의 인과 효과를 격리한 실험은 아니다. 창 평균은 서로 다른 주제의 신호를 희석할 수 있으나 개별 회귀의 원인으로 확정하지 않는다.

## 비용과 적용 판단

문서 처리 시퀀스는 52개에서 61개로 17.3% 증가했고, 질문 시퀀스는 24개로 동일하다. 이 작은 평가에서 저장 벡터 수는 52개 그대로다. 처리 시퀀스 수가 곧 지연시간 비율은 아니며 별도의 정식 latency benchmark는 수행하지 않았다.

**기본 적용은 보류한다.** @10 근거 완전 포함은 62.5%로 개선됐지만 @5는 같고 @1은 회귀했다. API는 기존 파일 단위 구성을 유지한다. 답변 생성·거절 성능도 아직 평가하지 않았다. 창 평균은 큰 문맥을 사용하는 실험의 비교 후보로 보존한다. 다음 후보는 창 벡터를 평균하지 않고 개별 창을 검색한 뒤 최대 유사도로 원문 청크에 합치는 방식이다. 긴 청크가 더 많은 창을 가져 생길 수 있는 편향도 함께 확인해야 한다.

## 검증과 재현

전체 pytest 75건과 Ruff 검사를 통과했다. 새 단위 테스트는 전체 payload·중첩·후미·특수 토큰·빈 입력·경계 길이·짧은 입력 동등성·출력 순서·청크당 벡터 하나를 검증한다. CLI 통합 테스트는 기본/창 모드 모두 모델·다운로드 대체로 네트워크 없이 실행한다.

최초 실행과 두 번째 실행의 결과 파일 해시는 달랐지만 차이는 저장 score 필드에 한정됐고 파일 순위·상위 청크 ID 순서·근거 지표는 같았다. 두 번째·세 번째 결과의 SHA-256은 `733c5d24e573312ef8029d871d97b0eb44d6efe86b45b4aac03e542d5e137651`로 일치했다. 다른 색인이나 환경에서의 전체 바이트 동일성은 보장하지 않는다.

기존 질문·근거·기준선·소스 해시가 보존됐고 새 결과의 모델 파일 해시는 기존 다국어 기준선과 모두 같았다. 기준선 원본과 API는 수정하지 않았다.

```powershell
.\.venv\Scripts\python.exe -m legacy_rag.evaluation.run_multilingual_baseline --windowed --local-files-only
```

기본 결과는 `data/evaluation/results/windowed-multilingual-baseline-v1.json`이다. `--windowed` 모드는 기존 다국어 기준선을 입력으로 선택하고 별도 collection과 결과 파일을 사용한다. 나머지 경로 옵션은 [다국어 기준선](multilingual-embedding-baseline.md)과 같다. 창·중첩·집계 방식은 이번 비교에서 고정했다.
