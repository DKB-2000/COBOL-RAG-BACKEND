# 로컬 Qwen3와 기존 API 비교

2026-10-28~29, 같은 공개 합성 COBOL5개와 고정30문항을 사용했다. **근거까지 충족한
정답은 기존 API와 Qwen3 모두15/24**였다. Qwen3는 더 많은 답변을 반환했지만,
근거 없는 질문의 올바른 거절은6/6에서4/6으로 줄었고 CPU 응답은 크게 느렸다.
이 구성에서는 내용 정답 수의 증가만으로 기존 API보다 좋다고 판단할 수 없다.

분모로 삼아 정확도를 부풀리지 않았다. 원자 사실 분모는 출력 내용이 달라 서로 다르다.
ID가 유효해도 인용 코드가 주장을 뒷받침하지 않을 수 있다.

이 PC에서 관측한 질의 지연은 p50 약54배, p95 약57배 길었다. 로컬 CPU와 원격 API의
실사용 구성 비교이며 동일 하드웨어에서의 모델 추론 속도 비교나 운영 SLA가 아니다.

## 개선과 회귀, 실패 사례

- **q002 개선:** Qwen3는 READ-CUSTOMER의 `READ CUSTOMER-IN / AT END`를 직접 인용했다.
  기존 API는 `invalid_citations`로 거절했다. Qwen3의 최초 절전 영향 실패와 재측정을 구분했다.
- **q024 회귀:** API는 반환 필드 `LK-FORMATTED-DATE`를 답했다. Qwen3는
  `YYYY-MM-DD` 형식과10자리 문자열만 설명해 질문이 요구한 필드명을 답하지 못했다.
- **q004/q005:** 전체 원본상 문단명은 맞아 내용 정답으로 판정했지만, q004는 무효 고객 분기의
  호출 근거가 빠졌고 q005는 다른 프로그램의 동명 MAIN-PROCESS를 인용했다.
  이2건은 근거까지 충족한 정답으로 계산하지 않았다. 기존 v1 q013의 보수적 인용 기준을 유지했다.
- **q003/q006/q011:** 파일 선언을 고객 검증으로, 계좌 상태 집계를 입출금 구분으로,
  보고서 처리를 거래 테이블 적재로 잘못 설명했다.
- **q026/q030:** 원문에 CICS 화면 전송과 XML 송장 생성이 없는데도 TRANSACTION-POST가
  해당 기능을 수행한다고 답했다. 인용은 PROGRAM-ID 선언뿐이었다.
  나머지 DB2·MQ·비밀번호·월말 삭제 질문은 올바르게 거절했다.

근거 충족 기준의 개선은q002, 회귀는q024로 순증0건이다. 더 많이 답하는 것과
근거에 맞게 답하는 것은 다르다. 이 평가에서는 형식·ID 검증만으로 막지 못한 환각이 확인됐다.

## 조건과 측정 범위

- 기존 API는 저장된 [생성 평가 v2](generation-evaluation-v2.md)를 사용했다.
  설정 모델은 `gpt-6-luna`이며 실제 공급자 model ID는 당시 관측하지 못했다.
  추가 유료 호출은 없었다.
- Qwen3는 `qwen3:4b`, GGUF Q4_K_M, digest
  `359d7dd4bcdab3d86b87d73ac27966f4dbb9f5efdfcc75d34a8764a09474fae7`이다.
  Ollama0.40.12, Core Ultra5 125U, RAM16GB이며 실행 중 `size_vram=0`으로 CPU 사용을 확인했다.
  모델 메모리 관측값은3,888,675,552바이트였다.
- identifier-aware 검색·공개52청크·최대10청크/원문4000자·질문·시스템 프롬프트·루브릭을 고정했다.
  각 실행 전30문항의 선택 문맥 ID/본문/경로/심볼이 기존 API 자료와 모두 일치함을 확인했다.
  별도의 재순위화 실험은 이 비교에 포함하지 않았다.
- Qwen3는 온도0, `think=false`, 문맥8192, 출력1024, timeout300초, 자동 재시도0이다.
  API는 출력1000·reasoning none이었다. 토크나이저와 공급자별 설정 차이는 남는다.
  모델·입력·코드 해시는 실행 구간 사이 일치함을 확인했다.
- 실제 순차 HTTP `/query` 시간에 검색·생성·검증·직렬화를 포함했다. 별도 `/search` 사전검사와
  오프라인 채점은 제외했다. 각30건, nearest-rank로 p50/p95를 구했다.
  Qwen3는 요청마다 `keep_alive=0`으로 모델을 내려 로딩 시간도 포함한다.

초기 예비 실행에서 Pydantic 스키마의 기본값 때문에 `claims`가 선택 항목으로 전달되는
차이를 발견했다. 기존 API의 strict 계약과 맞춰 `status/claims/reason` 모두 필수로 보정한 뒤
본 측정 조건을 고정했다. 보정 전 예비 실패도 로컬 산출물에 보존했다.

## 중단과 환경 재측정

사용자 재기동 요청으로11건 완료 후 중지했고, 재개 시 완료11건의 해시를 확인한 뒤
남은19건만 별도 파일에 수집했다. 중단 시 진행 중이던 미완료 시도도 journal에 남았다.

원본30건 중 q002/q018/q020/q021/q022는 설정 제한을 크게 넘는 HTTP timeout과
Windows 절전 구간이 겹쳤다. 요청 journal과 Kernel-Power506/507 시각의 교집합을 기록했다.
전원 상태 구간이 매 순간 비활동을 입증하는 것은 아니므로 모델 자체의 시간으로 단정하지 않았다.
이5건만 별도 prefix에서 각1회 재측정했다. 의미적 실패를 성공으로 바꾸기 위한 반복 호출은 하지 않았다.

| Qwen3 집계 | 최초 완료30건 | 환경 영향5건 별도 재측정 후30건 |
|---|---:|---:|
| answered / refused / error | 20 / 5 / 5 | 23 / 7 / 0 |
| 내용 정답 | 14/24 | 17/24 |
| 근거까지 충족 | 12/24 | 15/24 |
| 올바른 거절 | 4/6 | 4/6 |
| HTTP p50 / p95 | 107.139초 / 19461.421초 | 88.176초 / 173.417초 |

재측정에서는 q002/q020/q021이 정상 정답, q018/q022는 정상적인 근거 부족 거절이었다.
답변 가능한 두 문항의 거절은 정확도 성공으로 세지 않았다. 원본을 덮어쓰지 않고
완료 관측35건과 각 집계에 사용한30개 case ID를 구분했다.

## 재현 자료와 한계

[비교 JSON](../data/evaluation/results/ollama-generation-comparison-v1.json)에 문항별 최종 응답·
판정·개선/회귀·원본 환경 실패·별도 재측정·토큰/시간 분해·입력 및 산출물 해시가 있다.
원시 공급자 응답과 추론 필드는 공개 결과에서 제외하고 Git 제외 `artifacts/`에 보존했다.

`scripts/evaluate_ollama.py`의 기본 실행은 입력 확인만 수행한다. `--execute`는 실제 로컬
모델을 호출한다. `--resume-from`은 완료된 오류 결과도 자동 재호출하지 않고,
`--case-id`는 명시한 환경 재측정 문항만 별도 prefix에 기록한다. 기존 prefix는 덮어쓰지 않는다.
임시 자동 절전 방지는 실행 종료 시 해제되며 사용자 수동 절전/덮개 닫힘을 막지는 않는다.

이 결과는 개발에 사용한 작은 합성30문항이며 독립 holdout이나 실제 업무 코드 평가가 아니다.
의미 판정은 Codex1차 검수다. 재부팅·절전으로 실행이 분할됐고, 실행 중 가용 RAM이 약0.82GiB,
재개 전 약1.18GiB인 관측이 있어 전용 서버의 통제된 성능 벤치로 일반화할 수 없다.
로컬 전력·하드웨어 비용과 기존 API의 실제 청구액은 측정하지 않았다.
