# 호출·선언 관계 기반 문맥 보강 비교

## 고정 조건과 규칙

다국어 문맥화 구조 청크 기준선의 저장된 순위를 사용한다. 모델 추론·다운로드·재색인은 수행하지 않고 기존 52개 청크·질문 v1·근거 v1·원문을 유지한다. API는 변경하지 않았다.

선택 규칙은 결과 평가 전에 Task log에 고정했다. 정답 출처·기대 심볼·근거 주석은 관계 추출이나 문맥 선택에 전달하지 않는다. 소스에서 다음 관계만 추출한다.

1. `PROCEDURE DIVISION USING`과 같은 파일 `LINKAGE SECTION`의 계약 연결: 양방향.
2. 직접 `PERFORM <문단>` 대상과 호출자: 같은 파일에서 양방향.
3. `CALL "프로그램"`의 정적 대상: 고유 PROGRAM-ID로 식별한 파일의 IDENTIFICATION DIVISION·PROCEDURE DIVISION·LINKAGE SECTION과 양방향.
4. 코드에서 참조하는 같은 파일의 데이터 선언 청크: 참조 → 선언만 연결. 선언에서 모든 사용 문단으로 확산하지 않는다.

최초 검색 상위 5개를 seed로 유지하고 그 seed의 1-hop 이웃만 추가한다. 추가된 청크를 다시 확장하지 않는다. 위 관계 순서대로 우선하며 같은 종류는 seed 순위·출처·chunk_index 순으로 선택한다. 중복 ID는 제거한다. 최대 10개·원문 4,000자로 제한하고, 넘치는 청크는 통째로 건너뛴다. 원문을 잘라 근거를 훼손하거나 추가 청크에 임의의 벡터 점수를 부여하지 않는다. 추가 이유와 seed ID, 제외 ID는 결과 JSON에 보존한다.

비교군은 원래 상위 5개, 원래 상위 10개, 같은 10개·4,000자 제한을 적용한 원래 상위 10개다. 문자 예산은 토큰 예산이 아니며 동일 상한이지 동일 사용량 비교는 아니다. 이 실험은 검색 순위 재학습이 아니라 최종 문맥 선택이므로 파일 MRR 개선으로 보고하지 않는다.

## 결과

근거 완전 포함은 질문에 필요한 모든 근거 단위가 선택 문맥에 포함된 비율이다. 24개 answerable 질문을 평가한다.

| 문맥 선택 | 근거 완전 포함 | 평균 원문 문자 수 | 평균 청크 수 | 최대 원문 문자 수 |
|---|---:|---:|---:|---:|
| 원래 상위 5개 | 9/24 (37.5%) | 1,298.5 | 5.00 | 2,263 |
| 원래 상위 10개 | 13/24 (54.2%) | 2,348.0 | 10.00 | 4,056 |
| 상위 10개 + 4,000자 제한 | 13/24 (54.2%) | 2,336.0 | 9.96 | 3,767 |
| 상위 5개 + 1-hop 확장 | 12/24 (50.0%) | 2,787.5 | 9.46 | 3,955 |

확장은 상위 5개 대비 q009·q014·q024를 추가로 해결하고 기존 성공 9개는 유지했다. 그러나 같은 최대 예산의 상위 10개와 비교하면 q014만 개선되고 q001·q017은 놓쳤다. 평균 원문도 약 451.6자 더 길다. 심볼 포함률은 0.6597로 비교군 0.6042보다 높지만 근거 완전 포함률은 낮다. 심볼 포함만으로 채택하면 안 되는 사례다.

## 실패 질문과 입력 절단

상위 5개 실패 15건 중 q001·q009·q017·q024는 누락 근거 청크가 원래 상위 10개 안에 있다. 각각 저장 순위 9·7·9·10이다. 나머지 11건은 하나 이상의 필수 근거가 저장된 상위 10개 밖에 있다. 전체 순위는 저장돼 있지 않아 정확한 더 낮은 순위는 알 수 없다.

확장이 보완한 사례:

- q009: LINKAGE 선언 → USING 계약을 추가했다.
- q014: TRANSACTION-POST의 MAIN-PROCESS → PERFORM POST-TRANSACTIONS를 추가해 실제 CALL을 찾았다. 해당 근거는 원래 상위 10개에 없었다.
- q024: DATE-UTILITY의 본문·USING 참조 → LINKAGE 선언을 추가했다.

실패 15건 중 6건(q004·q005·q011·q012·q017·q018)은 128토큰을 초과하는 정답 청크를 요구한다. 이는 절단 관련성이지 원인 확정이 아니다. 로컬 캐시의 동일 tokenizer로 문맥화 입력을 128토큰 인코딩하고 token offset으로 실제 입력 접두 범위를 확인했다. q004·q005·q017·q018은 해당 접두 범위에도 근거 코드 조각이 모두 있었다. 반면 다음 조각은 범위 밖이었다.

- q011 LOAD-TRANSACTIONS: `MOVE TI-TYPE TO WS-TYPE(WS-TRANSACTION-COUNT)`, `MOVE TI-AMOUNT TO WS-AMOUNT(WS-TRANSACTION-COUNT)`
- q012 WORKING-STORAGE SECTION: `05 WS-TRANSACTION-ENTRY OCCURS 20 TIMES.`의 전체 구절

두 질문 모두 현재 검색 결과의 출처 선택에도 문제가 있으므로 입력 절단만 해결하면 성공한다고 단정할 수 없다. 후속 [긴 입력의 창 분할·평균 비교](windowed-embedding-baseline.md)는 동일 근거 기준의 별도 결과로 보존한다.

## 적용 판단과 한계

**이 규칙의 전체 적용은 보류한다.** 기본 비교군보다 근거 완전성이 낮고 평균 문맥이 길다. 특정 호출·계약 보강 사례의 가능성은 남기되, 평가 질문에 맞춰 우선순위를 재조정하지 않았다. API는 기존 파일 단위 구성을 유지하며 답변 생성 준비 완료로 처리하지 않는다.

추출기는 합성 고정 형식 샘플에 대한 제한적 어휘 분석이다. 고정 형식 주석·인라인 주석·문자열 내부의 가짜 호출은 제외한다. 동적 CALL, 모호한 중복 PROGRAM-ID, PERFORM THRU/THROUGH 범위는 추측해서 연결하지 않는다. COPY·전체 문법·데이터 흐름·별칭·조건별 도달성은 분석하지 않는다. 문자열 기반 근거 평가도 실제 답변의 의미적 정확성을 보장하지 않는다. 실패 질문을 이미 관찰한 개발셋 결과이며 독립 holdout 성능으로 해석하지 않는다.

## 검증과 재실행

전체 pytest 67건과 Ruff 검사를 통과했다. 테스트는 관계 방향·파일 경계·식별자 일치·주석과 문자열 제외·동적/모호한 호출 제외·1-hop·seed 유지·중복 제거·청크/문자 예산·코퍼스 순서 독립성·입력 덮어쓰기 방지를 검증한다. 통합 테스트는 고정 입력 해시 보존과 결과 재현성도 확인한다.
