# 아키텍처

## 목표

레거시 코드에 대한 질문을 받으면 관련 청크를 검색하고, 파일·심볼·청크 위치를 근거로 추적 가능한 답변을 반환한다. 초기 버전은 로컬 개발과 재현 가능한 품질 측정에 집중한다.

## 처리 흐름

```text
공개/합성 소스
  -> ingestion: 로딩 -> 정규화 -> 언어별 청킹 -> 메타데이터
  -> retrieval: 임베딩 -> Chroma 저장 -> 필터/유사도 검색
  -> generation: 검색 문맥 -> 근거 기반 답변 + 출처
  -> api: HTTP 계약

고정 평가셋 -> evaluation -> 검색/답변/성능 지표
```

## 경계

| 영역 | 소유하는 것 | 소유하지 않는 것 |
|---|---|---|
| `api` | 입력/출력 스키마, 상태 코드, 의존성 주입 | 청킹, 검색 알고리즘, 프롬프트 |
| `ingestion` | 소스 로딩, 정규화, 청크, 메타데이터 | HTTP, 답변 생성 |
| `retrieval` | 벡터 저장소, 검색·필터 정책, 문맥 조립 | 파일 파싱, HTTP |
| `generation` | 프롬프트, 인용 가능한 답변, 거절 정책 | 데이터 적재 |
| `evaluation` | 평가셋 로딩, 지표, 기준선 비교 | 프로덕션 요청 처리 |

## 데이터 계약

청크는 다음 필드를 잃지 않아야 한다.

- `chunk_id`: 동일 입력과 청킹 설정에서 재현 가능한 식별자
- `text`: 검색·생성에 사용하는 본문
- `source_path`: 데이터 루트 기준 상대 경로
- `language`: 예: `cobol`, `java`
- `symbol`: 프로그램, 섹션, 클래스 또는 메서드 이름
- `chunk_index`: 파일 또는 심볼 안의 순서
- `content_hash`: 변경 감지용 해시

검색 결과와 최종 답변은 `chunk_id`, `source_path`, 점수를 출처로 노출한다.

## 저장소 선택

초기에는 Chroma `PersistentClient`를 로컬 개발·테스트용으로 사용한다. 영속 디렉터리는 `data/chroma/`이며 Git에서 제외한다. 서비스 배포 단계에서 동시성, 백업, 접근 제어 요구를 측정한 뒤 서버형 저장소 여부를 별도로 결정한다.

## P4 계약 구현 상태

현재 API는 일반 다국어 구조·문맥화 검색을 별도 api-v2 collection에서 사용한다. `/query`는 검색된 원문 최대10개/4000자 문맥을 조립하고 `GenerationModel` port의 주장별 출처를 검증한다. 생성 공급자는 아직 미연결이며 기본 응답은 `unavailable`이다. 가짜 모델 검증은 실제 답변 품질을 보장하지 않는다. 상세 계약·검증·한계는 [`grounded-query-contract.md`](grounded-query-contract.md)를 따른다.

## 평가 게이트

- 검색: Hit@k, MRR, 필터 정확도
- 답변: 근거성, 인용 완전성, 답변 불가 질문의 거절 정확도
- 운영: 색인 시간, p50/p95 질의 지연시간, 저장 크기

청킹, 임베딩, 검색 파라미터 변경은 같은 평가셋의 기준선과 비교하며, 평균뿐 아니라 실패 사례도 보존한다.
