# 대표 데모 — 코드 검색과 근거 기반 답변

목표는 약 5분 안에 **한국어 질문 → 코드 위치 탐색 → 출처가 있는 답변 → 근거 부족 거절 → 평가와 한계**를 설명하는 것입니다. 공개 합성 샘플만 사용합니다.

검색은 로컬 API로 직접 시연하고, 생성 답변은 2026-10-27에 수집한 실제 평가 응답을 재생합니다. 저장 응답을 실시간 생성으로 표현하지 않습니다. 이 절차에는 추가 OpenAI 호출이 없습니다. 실시간 생성까지 촬영하려면 별도로 공급자 설정과 호출 범위를 정해야 합니다.

## 화면과 준비

IntelliJ에서 프로젝트 루트를 열고 다음 세 화면을 준비합니다.

1. PowerShell 터미널: 명령과 저장 응답 출력
2. 브라우저: `http://127.0.0.1:8001/docs`의 검색 API
3. 코드 편집기: `data/samples/customer-import.cbl`, `data/samples/transaction-post.cbl`

새 환경은 [README의 준비 절차](../README.md#빠른-시작--로컬-검색-데모)를 먼저 수행합니다. 이미 이미지와 모델이 있는 환경에서는 다음 명령으로 시작합니다.

```powershell
docker compose -f compose.yaml up -d --no-build --wait --wait-timeout 60
.\.venv\Scripts\python.exe -X utf8 scripts/verify_runtime.py --index --output artifacts/demo-preflight-01.json
```

`retrieval_ok`를 확인한 뒤 촬영합니다. 도구는 공개 5개 파일을 색인하고 검색을 검사하며 `/query`는 호출하지 않습니다. 출력 파일이 이미 있으면 `demo-preflight-02.json`처럼 새 이름을 사용합니다. 준비 실패를 생략하고 성공한 것처럼 촬영하지 않습니다.

Docker가 꺼져 있으면 Linux 엔진을 켜고, 이미지가 없으면 README의 build 단계부터 진행합니다. 모델 경로 오류는 [운영 안내](runtime.md)를 확인합니다. 기본 구성의 생성은 disabled이고 키를 전달하지 않습니다. 촬영 중 `/query`를 실행하는 대신 아래 저장 응답 표시 도구를 사용합니다.

| 0:30–1:40 | q001 검색 → 저장 답변 → 코드 | 파일을 여는 문단과 실제 `OPEN INPUT` 구문을 연결 |
| 1:40–2:40 | q014 저장 답변 → 호출 코드 | 프로그램 간 호출 대상을 근거와 함께 설명 |

## 장면 1 — 문단 검색과 코드 근거

Swagger에서 `POST /search` → **Try it out**에 아래 요청을 넣고 실행합니다.

```json
{
  "query": "고객 입력 파일을 여는 문단은 무엇인가?",
  "limit": 10
}
```

응답의 `results`에서 `samples/customer-import.cbl` / `OPEN-FILES`를 찾아 `text`, `chunk_id`, `symbol`을 보여줍니다. 1위라고 미리 단정하지 않습니다. 예상 문단이 없으면 현재 검색 결과와 저장된 평가 결과가 다르다는 점을 기록하고, 저장 응답이 지금의 검색으로 생성됐다고 말하지 않습니다.

터미널에서 당시 실제 생성 응답을 표시합니다.

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/show_demo.py --case q001
```

기대 내용: `OPEN-FILES` 문단에서 `OPEN INPUT CUSTOMER-IN`으로 연다는 답변과 출처입니다. 편집기의 [customer-import.cbl](../data/samples/customer-import.cbl)에서 `OPEN-FILES.`를 검색하고 실제 구문과 대조합니다.

발표 문장:

> 지금 검색은 로컬 API의 실제 결과입니다. 생성 답변은 화면에 표시된 날짜의 실제 평가 기록입니다. 답변의 문단명과 파일 경로를 따라 원문 구문까지 확인할 수 있습니다.

## 장면 2 — 프로그램 호출 관계

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/show_demo.py --case q014
```

질문은 “TRANSACTION-POST가 잔액 계산을 위해 호출하는 프로그램은 무엇인가?”입니다. 저장 답변은 `ACCOUNT-BALANCE`를 지목합니다.

[transaction-post.cbl](../data/samples/transaction-post.cbl)의 `POST-TRANSACTIONS.`에서 `CALL "ACCOUNT-BALANCE"`를 보여줍니다. 호출 관계를 설명하는 사례이며, 전체 호출 그래프나 COBOL 실행 의미 분석 기능을 구현한 것으로 표현하지 않습니다.

> 코드의 이름만 제시하는 데서 끝나지 않고, 호출 구문이 있는 문단을 근거로 제공합니다. 이 문항은 개선 전 거절에서 개선 후 정답·인용 충족으로 바뀌었습니다.

## 장면 3 — 근거 부족 거절

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/show_demo.py --case q025
```

질문은 “이 샘플에서 DB2 고객 테이블을 갱신하는 SQL 문은 무엇인가?”입니다. 저장 결과는 `refused / insufficient_evidence`이고 답변은 없습니다.

> 없는 SQL을 생성하는 대신 근거가 부족하다고 거절한 사례입니다. 평가에 포함된 근거 부족 6문항은 모두 거절했지만, 모든 종류의 환각을 차단한다는 의미는 아닙니다.

## 장면 4 — 개선 결과와 회귀

[평가 비교](generation-evaluation-v2.md)와 아래 회귀 사례를 보여줍니다.

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/show_demo.py --case q002
```

> 답변 가능한 24문항에서 정답과 충분한 인용을 모두 제공한 비율을 54.2%에서 62.5%로 개선했습니다. 개선 3건과 회귀 1건이 있었고, q002는 인용 검증 실패로 거절됐습니다. 검색에서 근거를 찾는 것과 최종 답변의 성공은 별개였습니다.

이어서 작은 합성 개발셋이며 Codex의 1차 채점이라는 한계를 말합니다. 전체 기대 동작 21/30(70%)은 정답·인용과 올바른 거절의 합이며, 답변 정확도 70%라고 표현하지 않습니다. 데모의 3개 사례만으로 전체 성능을 주장하지 않습니다.

## 장면 5 — 실행과 마무리

준비 단계의 `retrieval_ok`와 [운영 검증 기록](runtime.md)을 보여줍니다.

> Linux 컨테이너를 재생성한 뒤 재색인 없이 같은 검색의 상위 10청크가 보존되는 것을 확인했습니다. 인증·HTTPS·외부 배포와 다중 사용자 운영 검증은 남아 있고, 현재는 같은 PC에서 실행하는 데모입니다.

준비 단계에서 생성한 보고서는 오늘의 검색 확인 자료입니다. 컨테이너 재생성 검증은 10월 27일의 기록이며 오늘 다시 수행한 것으로 설명하지 않습니다. 직접 재생성 시연까지 하려면 [README의 영속성 확인 단계](../README.md#3-컨테이너-재생성-후-검색-결과-보존-확인)를 추가합니다.

- [ ] 실제 검색과 저장된 생성 응답의 실행 시점을 구분함
- [ ] q001·q014의 답변을 공개 원문과 직접 대조함
- [ ] q025 거절과 q002 회귀를 설명할 수 있음
- [ ] 62.5%의 분모와 소규모 개발셋·1차 채점 한계를 설명함
- [ ] 화면에 키·환경변수 전체·로컬 전용 COBOL이 나타나지 않음
- [ ] 촬영 영상과 사용자 직접 재현 확인을 별도로 완료함

시나리오 준비와 실제 촬영·독립 검수는 별도 작업입니다. 도구는 공개 결과 JSON을 읽기만 하며 앱·색인·평가 원본을 변경하지 않습니다.
