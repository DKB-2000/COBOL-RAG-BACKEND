# Legacy Code RAG Backend 실행 로드맵

## 목표와 전제

목표는 레거시 코드를 검색하고 근거와 함께 답변하는 RAG 백엔드를 로컬 MVP에서 배포 가능한 포트폴리오까지 완성하는 것이다.

- 1인 개발 기준 8주 권장 일정
- 공개 라이선스 또는 합성 COBOL 데이터만 사용
- 검색 품질을 먼저 증명한 뒤 답변 생성과 클라우드로 확장
- 초기 저장소는 Chroma, 서비스 API는 FastAPI 사용
- 모델·임베딩 공급자는 구현 단계에서 비용·재현성 기준으로 별도 결정

## 우선순위 요약

| 우선순위 | 단계 | 권장 기간 | 선행 조건 | 통과해야 다음 단계로 이동 |
|---|---|---:|---|---|
| P0 | 범위·평가셋 고정 | 1주 | 없음 | 샘플과 평가 질문이 버전 관리됨 |
| P1 | 수집·메타데이터 기준선 | 1주 | P0 | 같은 입력에서 같은 청크 ID 생성 |
| P2 | 청킹·Chroma 검색 | 1주 | P1 | 검색 기준선과 실패 사례 확보 |
| P3 | FastAPI 검색 서비스 | 1주 | P2 | 색인·검색 API와 출처 계약 검증 |
| P4 | 근거 기반 답변 생성 | 1주 | P3 | 인용과 답변 불가 정책 동작 |
| P5 | 평가·회귀 자동화 | 1주 | P4 | 기준선 비교 결과를 재현 가능 |

| P7 | GitHub·면접 산출물 | 1주 | P6 | 제3자가 README만으로 재현 가능 |

## P0 — 범위와 평가셋 고정

가장 먼저 무엇을 잘해야 하는지 고정한다. 코드를 많이 작성하는 것보다 이 단계가 우선이다.

### 작업

1. 합성 COBOL 프로그램 5~10개 작성
2. 파일 I/O, 분기, PERFORM, 데이터 구조, 프로그램 호출 사례 포함
3. 평가 질문 30~50개 작성
4. 정답 가능 질문과 답변 불가 질문을 함께 구성
5. 각 질문에 기대 파일과 심볼을 연결

### 산출물

- `data/samples/*.cbl`
- `data/evaluation/questions-v1.jsonl`
- 데이터 출처·라이선스·생성 규칙 문서

### 완료 기준

- 모든 질문 ID가 고유함
- `expected_sources`, `expected_symbols`, `answerable`이 채워짐
- 사람이 소스만 읽고 정답 근거를 확인할 수 있음
- 평가셋을 보고 청킹 규칙을 맞추지 않도록 v1을 고정함

## P1 — 수집과 메타데이터 기준선

### 작업

1. `.cbl` 파일 로더 구현
2. 인코딩, 줄바꿈, 빈 파일 처리 규칙 확정
3. 파일 단위 기준선 청킹 구현
4. 재현 가능한 `chunk_id`, `content_hash` 생성
5. 메타데이터 계약을 타입과 테스트로 고정

### 완료 기준

- 같은 파일과 설정에서 같은 청크 ID가 생성됨
- `source_path`, `language`, `symbol`, `chunk_index`, `content_hash`가 보존됨
- 잘못된 확장자·빈 파일·중복 입력의 동작이 테스트됨

## P2 — 청킹과 Chroma 검색

파일 단위 기준선을 먼저 측정한 다음 COBOL 구조 기반 청킹으로 개선한다.

### 작업

1. 임베딩 공급자 선택 기록: 비용, 오프라인 가능 여부, 차원, 재현성
2. Chroma `PersistentClient` adapter 구현
3. 전체 재색인과 변경 파일 갱신 구분
4. 파일 단위 청킹 검색 기준선 측정
5. `DIVISION`·`SECTION`·`PARAGRAPH` 기반 청킹 추가
6. top-k와 메타데이터 필터 비교

### 잠정 품질 게이트

- Hit@5 ≥ 0.80
- MRR ≥ 0.60
- 동일 데이터·설정에서 평가 결과 재현
- 실패 질문을 청킹·임베딩·질문 모호성으로 분류

최초 기준선이 지나치게 낮으면 수치 자체를 숨기지 말고 원인과 조정 근거를 기록한다.

## P3 — FastAPI 검색 서비스

### 최소 API

| Method | Path | 목적 |
|---|---|---|
| `GET` | `/health` | 서비스 상태 |
| `POST` | `/documents/index` | 허용된 데이터 루트 색인 |
| `POST` | `/search` | 검색 결과와 점수·출처 반환 |
| `POST` | `/query` | P4에서 근거 기반 답변 반환 |

### 완료 기준

- 라우트는 HTTP 검증·직렬화만 담당
- 절대 경로 유출과 데이터 루트 이탈을 차단
- 검색 응답에 `chunk_id`, `source_path`, `symbol`, 점수가 포함됨
- 단위 테스트와 API 경계 통합 테스트가 분리됨
- OpenAPI에서 요청·응답 계약을 확인할 수 있음

## P4 — 근거 기반 답변 생성

### 작업

1. 검색 문맥 조립 규칙 정의
2. 답변·출처·신뢰 부족 상태를 포함한 응답 스키마 작성
3. 검색 근거 밖의 추측을 금지하는 프롬프트 작성
4. 근거가 부족하거나 충돌하면 답변 불가 처리
5. 모델 호출을 interface 뒤에 두어 검색 테스트와 분리

### 완료 기준

- 모든 답변 문장 또는 핵심 주장에 출처가 연결됨
- 검색 결과가 없으면 모델을 호출하지 않거나 명시적으로 거절함
- 모델 장애가 검색 기능까지 중단시키지 않음
- 비밀키와 프롬프트 입력에 민감 데이터가 기록되지 않음

## P5 — 평가와 회귀 자동화

### 작업

1. retrieval 평가 runner 구현
2. 답변 근거성·인용 완전성·거절 정확도 측정
3. 색인 시간, 저장 크기, p50/p95 지연시간 기록
4. 설정과 결과를 JSON으로 보존
5. 이전 기준선 대비 회귀 판정

### 잠정 릴리스 게이트

- Hit@5 ≥ 0.80, MRR ≥ 0.60
- 인용 완전성 100%
- 답변 불가 질문 거절 정확도 ≥ 0.80
- 대표 실패 사례와 원인이 결과 보고서에 포함됨
- 청킹·임베딩·top-k 변경 시 동일 평가셋 결과가 자동 비교됨

LLM judge는 보조 지표로만 사용하며, 외부 모델 비용과 승인을 먼저 확인한다.

## P6 — 운영화와 클라우드 배포

검색·답변 품질 게이트를 통과한 뒤 시작한다.

### 작업

1. Docker 이미지와 환경 변수 계약 작성
2. 구조화 로그, 요청 ID, 타임아웃, 오류 응답 추가
3. AWS 단일 인스턴스 배포부터 시작
4. API 키는 배포 환경의 secret으로 주입
5. Chroma 데이터의 영속 볼륨과 백업 방법 기록
6. smoke test와 비용 종료 절차 작성

### 완료 기준

- 새 환경에서 문서만 보고 배포 가능
- 배포 URL에서 `/health`, `/search`, `/query` 확인
- 비밀정보가 이미지·로그·저장소에 없음
- 월 예상 비용과 서비스 종료 방법이 문서화됨

초기 포트폴리오에서는 Kubernetes, 다중 리전, 서버리스 분산 구조를 도입하지 않는다.

## P7 — GitHub와 면접 산출물

### 필수 문서

- 문제 정의와 대상 사용자
- 아키텍처 다이어그램
- 데이터·청킹·검색 선택 이유와 트레이드오프
- 정량 평가 표와 대표 실패 사례
- 로컬 실행·테스트·배포 방법
- API 요청·응답 예시
- 보안과 데이터 라이선스 설명

### 포트폴리오 완료 기준

- 처음 보는 사람이 15분 안에 로컬 실행 가능
- 데모 질문 3개와 답변 불가 질문 1개가 재현됨
- “왜 이 청킹인가”, “어떻게 hallucination을 측정했는가”, “운영 시 무엇을 바꿀 것인가”에 수치와 근거로 답할 수 있음
- 3~5분 데모 영상 또는 GIF가 있음

## 지금 바로 진행할 작업

첫 구현 task는 **P0 평가 데이터 v1**이다.

1. 합성 COBOL 샘플의 주제 5개 선정
2. 각 샘플에 검증할 심볼과 관계 정의
3. 질문 30개 초안 작성: 정답 가능 24개, 답변 불가 6개
4. 데이터 규약에 맞춰 JSONL 검증
5. P1 로더가 만족해야 할 입력·출력 사례 확정

P0가 끝날 때까지 임베딩 모델 선택, 프롬프트 튜닝, AWS 배포는 시작하지 않는다.
